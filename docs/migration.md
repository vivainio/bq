# Migrate from NServiceBus in phases

Start with a small group of endpoints whose senders and receivers can switch together. A send-only Bq producer and a subscriber without saga state make a useful first exercise. List the commands, events, subscriptions, and queues each endpoint uses before choosing the group.

Bq uses MessagePack. Give migrated consumers their own queues and use a distinct event exchange for the Bq group while legacy XML consumers remain active. Route commands to the new queues only when their receivers are ready. Before redirecting each flow, account for messages already queued, scheduled deliveries, and unpublished outbox entries. For flows with active sagas, decide how to handle existing state and pending timeouts before switching traffic.

## Port the endpoint

Use the `Bq.Messaging` APIs in the selected C# projects. Bq provides optional `IMessage`, `ICommand`, and `IEvent` markers. The host can use them when discovering handlers and configuring routes or subscriptions. Use [stable contract names](endpoints.md) to keep routing independent of CLR namespace changes.

Register incoming behaviors with `configuration.Incoming.Use` or register a `Behavior<IIncomingLogicalMessageContext>` with `configuration.Pipeline.Register`. Register a `Behavior<IIncomingPhysicalMessageContext>` the same way to run before transport mutators, type resolution and deserialization. It sees the received `IncomingMessage` with editable text headers, can replace the body through `UpdateMessage`, and can short-circuit by skipping `next()`. Physical behaviors run inside each delivery attempt, wrap the logical stage, and use their own ordering among physical steps. Recovery keeps the original wire body. Register an `IManageUnitsOfWork` factory with `RegisterUnitOfWork` to begin units before the physical stage and end them in reverse order, passing the failure to `End`. `Headers` holds the NServiceBus header names, and `LogManager`, `ILog` and `ILoggerFactory` (in `Bq.Messaging.Logging`) match the NServiceBus logging API, writing to `System.Diagnostics.Trace` by default. `RegisterComponents`, `UseContainer` and `GetSettings()` follow the NServiceBus shapes. Bq ships a small constructor-injection container, and `UseContainer(IContainer)` plugs in another one. Each message attempt gets a child `IBuilder`, available as `Builder` on behavior contexts and disposed when the attempt ends. `Feature`, `FeatureConfigurationContext`, `FeatureStartupTask`, `EnableFeature` and `DisableFeature` follow NServiceBus. Scanning discovers features, defaults apply first, and a feature sets up once its dependencies are active. Startup tasks run synchronously inside `RabbitEndpoint.Start` after the consumer is created and stop in reverse order during `StopAsync`. Outgoing behaviors for `IOutgoingSendContext`, `IOutgoingPublishContext`, `IOutgoingReplyContext`, `IOutgoingLogicalMessageContext` and `IOutgoingPhysicalMessageContext` register through the same `Pipeline.Register`. The operation stage runs first, then the logical stage around message mutators and serialization, then the physical stage around transport mutators. Header edits carry through each stage, `UpdateMessage` replaces the instance or body, and `RoutingStrategies` is read-only. `Behavior<IInvokeHandlerContext>` wraps each non-saga handler invocation and exposes the handler instance, the message and its metadata. Register an `IMutateIncomingMessages` instance with `RegisterMessageMutator` to edit the deserialized message or its text headers. An `IMutateIncomingTransportMessages` instance can edit bytes and text headers before deserialization. Bq runs these transport mutators after the native `MutateIncoming` callback and preserves the received wire message for recovery. An `IMutateOutgoingMessages` instance can edit text headers or replace the outgoing object before serialization. Replacements must implement the declared contract, which still governs routing. An `IMutateOutgoingTransportMessages` instance can edit serialized bytes and text headers before Bq persists or publishes a new outgoing message. It runs after the native `MutateOutgoing` callback. Logical steps run in registration order. Before starting the endpoint, use `Pipeline.Replace(stepId, ...)` to replace a registered behavior in place or `Pipeline.Remove(stepId)` to remove it. Use `UpdateMessageInstance` to pass a replacement to downstream behaviors and the handler. The replacement must implement the incoming message contract. Edit `IIncomingLogicalMessageContext.Headers` to share text header changes with downstream behaviors and the handler's `MessageHeaders`. Raw AMQP headers, forwarding, and recoverability use the transport values. Logical behaviors share the attempt-local `MessageHandled` flag. Bq sets it when handler invocation succeeds, and a behavior that short-circuits can set it itself. Logical behaviors and handlers share the `IMessageProcessingContext` APIs for sending, publishing, replying, and forwarding. Type registration requires a public parameterless constructor. Container-based behavior factories and other pipeline stages require adaptation. They can share attempt-local state, short-circuit processing, and wrap handler execution. Await `next()` once to continue processing. Use `configuration.Incoming.BeforeCommit` for application work that must commit with the inbox claim and outbox entries. Configure one database per endpoint for both application data and Bq persistence. Pass the supplied connection and transaction to the application data layer. An exception from the handler, callback, or surrounding behavior rolls back the transaction. If an outer behavior catches a downstream failure and returns, Bq still sends the failure to recoverability.

Transport mutators can change headers, the contract name, or the body. The outbox stores the outgoing mutator’s final contract name, headers, and body. Bq preserves the received wire payload for [recovery and replay](recoverability.md). Incoming behaviors can read the contract name, retry counts, and deferred or saga-timeout flags from the incoming context. Use `FindHeader` or `GetHeader` for text values such as `MessageHeaders.TimeSent`.

## API differences from NServiceBus 7

The comparison uses the [NServiceBus 7.8.6 source tag](https://github.com/Particular/NServiceBus/tree/7.8.6). Use Bq’s namespaces when porting code.

- Provide the RabbitMQ URI and persistence provider explicitly. Register routes, handlers, and sagas in the host. See [endpoint configuration](endpoints.md) and [saga registration](sagas.md).
- Use the application's ADO.NET connection and transaction from `SynchronizedStorageSession` for provider-specific work. See [persistence](persistence.md).
- Adapt custom saga finders and container-backed pipeline factories for Bq. See [saga correlation](sagas.md) and [Castle Windsor integration](windsor.md).

## Verify the migration locally

Run `bash scripts/test-rabbitmq.sh` to exercise the following cases with RabbitMQ and SQLite. The [integration test instructions](testing.md) also show how to run the transport-free cases on their own.

| Migration concern | What the tests verify |
| --- | --- |
| Routing and cutover | A send-only producer uses configured conventions to route a command and subscribe to an event. The migrated subscriber receives MessagePack while the simulated legacy consumer receives XML on a separate exchange. |
| Behaviors and application transactions | Each attempt resolves handlers and runs before-commit work in the same host scope. Short-circuiting skips handler resolution. A failed attempt rolls back the inbox claim, application writes, and outbox entries. |
| Send options and metadata | Relative and absolute delays, send and reply headers, publish headers, stable contract names, and incoming retry and saga-timeout metadata survive the expected transport or persistence path. |
| Transport mutation and replay | The outbox stores the mutated wire payload before publishing. Recovery retains the original received bytes so replay can run the incoming mutator again. |
| Recoverability and outages | Policies select immediate retry, delayed retry, or direct error routing. A retry gets a freshly deserialized message. Failed publications stay pending, and the critical-error hook reports a stalled dispatcher or sustained broker outage. |
| Sagas and test doubles | Saga correlation, completion, and durable timeouts run through RabbitMQ. Transport-free tests capture messages and timeout requests with `Bq.Testing`. |

The local fixtures use representative Bq endpoints. Production cutover still requires verification against the consuming application's contracts, topology, and database. The Oracle adapter accepts a host-supplied Devart or ODP.NET connection. Live Oracle and shared EF6 transaction verification require a database and the selected driver.
